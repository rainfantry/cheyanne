Section 01

Research Overview

Operation VADER is a security research project investigating Windows Defender's monitoring architecture on a live Windows 11 Home system with full Real-Time Protection enabled. All work was conducted on personally-owned hardware as part of cybersecurity coursework (CSEC — Tactical Cyber Operations).

The research began as a TOCTOU race condition study against Windows Defender's quarantine pipeline (vader-toctou, 6 engagements, 30 findings). That campaign was defeated by Microsoft's defense-in-depth — content re-verification, single-handle architecture, kernel-mode I/O bypass. The defenses held, but the research mapped Defender's internal architecture and informed subsequent investigation.

The second phase focused on identifying monitoring blind spots in Defender's tamper protection. This led to the discovery of a hardware breakpoint technique that bypasses AMSI and ETW monitoring without modifying target memory — a finding reported to Microsoft via MSRC as VULN-195458. Microsoft's response: "Won't Fix" — classified as not meeting the severity bar for servicing.

A separate CWE-732 privilege escalation was discovered in a third-party service configuration, enabling Standard User to SYSTEM escalation with no UAC prompt. This was independently documented and reported.

Section 03

Research Methodology

Reconnaissance

Automated scanning of the target system to identify services, their privilege levels, binary locations, file permissions, and DLL dependencies. Results scored for potential attack surface.

Hypothesis Testing

Each potential vulnerability was tested iteratively. When a defense held (e.g., manifest hardening blocked DLL sideloading), the finding was documented and the approach pivoted.

Evasion Analysis

Defender's detection capabilities were tested against known techniques to map which behaviors trigger alerts and which do not. This identified the hardware breakpoint blind spot.

Iterative Documentation

Every engagement produced numbered findings, regardless of success or failure. Failed attacks document working defenses. Successful bypasses document gaps for remediation.

Prior Art Integration

30 findings from the vader-toctou campaign (Defender quarantine TOCTOU research) fed directly into the second phase. Architecture knowledge of Defender's defense-in-depth guided all subsequent testing.

Responsible Disclosure

Findings meeting severity thresholds were reported to Microsoft via MSRC before any public documentation. The research timeline accommodated Microsoft's review process.

Section 05

Primary Finding — Defender HWBP Blind Spot

MSRC VULN-195458

Windows Defender's tamper protection monitors memory-level modifications to security-critical functions (VirtualProtect calls, byte writes to code regions, known patch patterns). However, it does not monitor CPU debug register manipulation.

Hardware breakpoints, set via the standard Windows API SetThreadContext, can intercept security functions without modifying a single byte of target memory. Both AMSI (script scanning) and ETW (process telemetry) can be simultaneously neutralised using this technique. The result: all user-mode security telemetry goes blind with zero memory modification.

This was reported to Microsoft via MSRC as VULN-195458. Microsoft's response classified it as not meeting the severity bar for servicing — "Won't Fix".

Why This Matters

Classic AMSI/ETW bypass techniques modify target function memory (e.g., patching the function prologue). Defender detects these via tamper protection and terminates the process. The hardware breakpoint approach avoids this entirely — the target code remains byte-identical, no VirtualProtect call is made, and no behavioral rule fires.

Detection Gap

Attribute Classic Patch Hardware Breakpoint
VirtualProtect called Yes No
Target memory modified Yes — bytes patched Zero bytes modified
Defender detection DETECTED & TERMINATED NOT DETECTED
Binary quarantined Yes (retroactive ML flag) No (persists on disk)
Underlying mechanism Code modification (user-mode) CPU debug registers (kernel state)

Architectural Root Cause

SetThreadContext is a standard Windows API. Setting debug registers on your own threads is a legitimate debugging operation. No behavioral rule currently exists for debug register manipulation targeting security-critical functions.

The kernel ETW-Ti provider exposes an event (EtwTiLogSetContextThread) that should fire when SetThreadContext modifies debug registers. If it fires but Defender ignores it, that is a consumer gap. If it does not fire for same-thread operations, that is a provider gap. Either way, the bypass works on current Windows 11 with full Defender RTP.

Section 06

Privilege Escalation — CWE-732

Vulnerability

A third-party service was discovered running as LocalSystem (highest privilege) with Auto start mode, but its binary resides in a per-user directory with overly permissive ACLs granting all users full control over the executable.

A standard user can replace the service binary. On next service restart or system reboot, the Service Control Manager loads the replacement with NT AUTHORITY\SYSTEM privileges. No admin credentials are entered and no UAC prompt is triggered.

Discovery Process

  1. Automated reconnaissance identified SYSTEM-level services with insecure file ACLs via PE import parsing and permission auditing
  2. A service was found with its binary in a user-writable directory — ACLs granted all standard users full control
  3. The vulnerability was verified: binary replacement succeeded without elevation, and the service loaded the replacement as SYSTEM on restart
  4. Finding documented with canary evidence (execution proof logging privilege level and context)

Cross-User Limitation

On multi-user systems, NTFS ACLs prevent cross-user access to per-user AppData directories. CWE-732 requires the vulnerable service binary to be under the attacker's own user profile or a world-writable location. This was confirmed as a mitigating factor on shared machines.

Section 08

Remediation Recommendations

The following recommendations address the gaps identified during this research. Items 1–3 address the CWE-732 privilege escalation vector. Items 4–5 address the hardware breakpoint monitoring gap (VULN-195458).

  1. Restrictive ACLs on all SYSTEM service directories and binaries. Service executables and their parent directories should be writable only by SYSTEM and BUILTIN\Administrators. No user-writable SYSTEM services.
  2. Service binaries must not reside in per-user AppData paths. %ProgramFiles% or %SystemRoot% enforce proper ACL inheritance by default. AppData directories inherit permissive user ACLs.
  3. Digital signature verification on service binaries at SCM level. The Service Control Manager should optionally verify Authenticode signatures before loading service executables, similar to driver signature enforcement.
  4. Behavioral rules for SetThreadContext targeting security DLLs. Defender should detect SetThreadContext calls that set debug registers to addresses within security-critical modules such as amsi.dll and ntdll.dll.
  5. Hardware breakpoint monitoring via EtwTiLogSetContextThread. The kernel ETW-Ti provider already exposes EtwTiLogSetContextThread. Defender (or a dedicated consumer) should subscribe to this event and alert when debug registers target security function addresses.
